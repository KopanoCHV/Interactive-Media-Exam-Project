Climb Up

Project Information

Live Demo:

Role: Frontend and Backend developer

Timeline: 24 February 2026 - 11 March 2026

Project Overview

The goal for this prototype was to explore a certain mechanic by forming a hypothesis about how the mechanic affects players gameplay experience. And the mechanic that was being explored was the multi-jump mechanic. This mechanic is like the normal jumping mechanic but instead of just allowing the player to just jump only if they are touchig the ground, this mechanic allows players to also jump even while they are in the air. This allows the player to kind of "fly" even when in reality they are just jumping. To be able to test this mechanic, there should be obsticles or an environment that forces the player to use the mechanic. When the prototype was being implemented there are few main features that had to be implemented, these features includes:

  • Environment
  • Enemies
  • Level UI

Implementation Process

1. Environment

When the prototype environment was implemented, it was made in a way that players are forced to use the multi-jump mechanic. Since the goal of the prototype was for players to reach the highest point of the map buy jumping from one level of the map to another, the levels were made to be far from each to a point were the normal jumping mechanic (one jump) would not be enough to cover the distance. And to also make the prototype a little more challenging, there were some points on the map were the grounds in some levels were made to move to make it hard for players to get on top of them. And to make sure that players dont get frustrated or tired from playing, the map have safe levels implemented, where there are no enemies and grounds are static allowing players to catch their breath. The environment also uses colors to tell the player how easy or difficult the map is as the player reaches higher grounds of the map.

Challenges:

Spacing between grounds

When the environment was being built, I had a challenge with getting the right space between grounds that would not make the prototype feel too easy due to the width of the spaces between grounds being too big. And there were some points in the game were players would just force themself through gaps just to avoid taking path they are meant to take. To fix these bugs, I had to play the game multiple times making sure that every space have the correct size, making the game not too easy for players and at the same time not too difficult.

Colliders

When playtesters were given the prototype to playtest, there were points were the character would just go through grounds if the players pushed themselves through hard enough. This was caused by the unity colliders not being the same size as the object (ground). A collider is a attribute that can be added to an object to stop players or any other objects from being able to go through the object (if that object has a collider too). To fix this, I had to go through all the grounds, making sure that their colliders have the same size as them.

2. Enemies

The enemies in the prototype are made to patrol around the map floor without reacting to the player when they are around. If the player touches the enemy they start the prototype from the start (level 0). This challenges players to avoid being touched by the enemies while they go up the map. The number of enemies per level increase as the player goes up the map. And to make the game more interesting, the patrol pattern of the enemies also change as the player goes up the map. And the other thing that changes as the player goes up the map is the speed at which the enemies patrol. This makes players enjoy the game more since the prototype feels progresive, and allows the players to enjoy playing the prototype as they go up.

Challenges:

Patrol System

When the prototype was play tested, there was a problem of the enemies moving out of the game screen instead of moving back and forth. To explain the problem, I will first need to explain how the patrol system work. For one patrolling guard, one square is needed to represent the guard and two empty objescts are needed to act as points that the guard need to patrol between (turnning points). The square (guard) is then made to move in a straight line in one direction. The points are then positioned in points where the guard need to change direction on. The empty objects are then made to change the square's direction every time they come in contact with it. But what caused the square to move out the game screen, was because some empty objects that were supposed to change the guards direction were not properly aligned with the square leading to the square missing the empty object completely and continued to move the same direction.

3. Level UI
